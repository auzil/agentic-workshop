What is an agent?

An agent is an LLM in a loop.
On each turn, the model does exactly one of two things:

✓ Emits text

We're done. Return it to the caller.

⚙ Emits tool calls

Execute them, feed results back, loop.

That's the whole pattern. No framework needed.

The loop

┌────────┐ prompt ┌─────────────────┐ tool calls ┌──────────┐ │ user │──────────▶│ Agent │─────────────▶│ tools │ └────────┘ │ (LLM in loop) │◀─────────────│ │ │ │ results └──────────┘ └─────────────────┘ │ │ final text answer ▼
Key insight: the model decides when it's done — not the programmer. The loop only exits when the model returns text (or we hit maxSteps).

The conversation is a list

Everything the agent "knows" lives in ChatCompletionMessageParam[].

// Four roles — each a different node in the conversation
{ role: 'system',    content: '...' }       // instructions — sent every turn
{ role: 'user',      content: '...' }       // the user's input
{ role: 'assistant', content: '...', tool_calls: [...] } // model's turn
{ role: 'tool',      tool_call_id: '...',   // result of one tool call
                     content: '...' }

The agent loop is mostly bookkeeping over this list: append the model's turn, append each tool result, repeat.

The loop, step by step

  • 1
    Init history with system + first user message.
  • 2
    Call chat.completions.create with history + tool declarations.
  • 3
    Read response.choices[0].message.
  • 4
    If tool_calls is empty → log the text, return. Done.
  • 5
    Otherwise: append the assistant's tool-call turn to history.
  • 6
    Execute each tool (Promise.all), append one role: 'tool' message per result.
  • 7
    Loop. If we hit maxSteps, throw.

Why order matters

The API enforces a strict message ordering. Get it wrong and you get a 400.

Turn 1 ────────────────────────────────────────────── [system] "You are a math tutor…" [user] "What is 47 * 12?" ────────────────────────────────────────────────────── ← model responds with tool_calls ────────────────────────────────────────────────────── Turn 2 ────────────────────────────────────────────── [system] "You are a math tutor…" [user] "What is 47 * 12?" [assistant] tool_calls: [{ name:"calculator", args:{…} }] ← append FIRST [tool] tool_call_id:"…", content:"564" ← THEN result ────────────────────────────────────────────────────── ← model responds with final text

Tools: what the model sees

The Tool interface in src/core/tool.ts maps to the OpenAI function-calling spec. 

export interface Tool<TResult = unknown> {
  readonly name: string;         // the function name the model calls
  readonly description: string;  // how the model decides WHEN to use it
  readonly parameters: ToolParameters; // JSON Schema — shapes the args
  readonly execute: (args: Record<string, unknown>) => Promise<TResult>;
}

Most agent failures are tool-design failures.
The name, description, and parameter schema are the model's only way to understand a tool.

The calculator tool

src/tools/calculator.ts — the first tool students use. 

export const calculator: Tool<{ result: number }> = {
  name: 'calculator',
  description: 'Evaluate a mathematical expression and return the result.',
  parameters: {
    type: Type.OBJECT,
    properties: {
      expression: {
        type: Type.STRING,
        description: 'A valid JavaScript math expression, e.g. "47 * 12"',
      },
    },
    required: ['expression'],
  },
  execute({ expression }) {
    const result = Function(`'use strict'; return (${expression})`)();
    return { result: Number(result) };
  },
};

export const DEFAULT_MODEL = process.env['AZURE_OPENAI_MODEL'] ?? 'gpt-4o';

let instance: AzureOpenAI | undefined;

export function getLlm(): AzureOpenAI {
  if (instance) return instance;
  // Validates credentials and throws clearly if any are missing
  const apiKey    = process.env['AZURE_OPENAI_API_KEY'];
  const endpoint  = process.env['AZURE_OPENAI_ENDPOINT'];
  const apiVersion = process.env['AZURE_OPENAI_API_VERSION'];
  if (!apiKey)     throw new Error('AZURE_OPENAI_API_KEY is not set…');
  // …
  instance = new AzureOpenAI({ apiKey, endpoint, apiVersion });
  return instance;
}

Lazy singleton — importing this file at type-check time does not require credentials.

AgentConfig — what you pass in

src/core/agent.ts

export interface AgentConfig {
  readonly name: string;         // appears in every log line
  readonly instructions: string; // system prompt — the model's persona
  readonly tools?: readonly Tool[];
  readonly model?: string;       // defaults to DEFAULT_MODEL from .env
  readonly maxSteps?: number;    // hard cap — defaults to 10
}
The constructor is already implemented. Your job is the run() method.

The run() skeleton

The shape to implement — every step maps to what you just learned. 

async run(input: string): Promise<string> {
  const messages = [
    { role: 'system',  content: this.instructions },
    { role: 'user',    content: input },
  ];
  const tools = toOpenAITools([...this.tools.values()]);

  for (let step = 0; step < this.maxSteps; step++) {
    this.logger.llmCall(this.model, [...this.tools.keys()]);
    const response = await getLlm().chat.completions.create(
      { model: this.model, messages, ...(tools.length ? { tools } : {}) }
    );
    const message   = response.choices[0]?.message;
    const toolCalls = message.tool_calls ?? [];

    if (toolCalls.length === 0) { /* → return text */ }

    messages.push({ role: 'assistant', ...message }); // ← must come first
    const results = await Promise.all(toolCalls.map(call => /* execute */));
    messages.push(...results);
  }
  throw new Error(`Agent ${this.name} exceeded maxSteps.`);
}

Agent loop — when to use it

✓ Good fit

  • Open-ended problems where the number of steps is unknown upfront
  • Research tasks that require exploring and backtracking
  • Any task where the model needs to decide which tools to call and in what order

✗ Poor fit

  • Latency-sensitive tasks (loops add turns)
  • Untrusted environments (unbounded tool use)
  • Fixed, known paths — use a workflow (W2–W4) instead

Anthropic: "Workflows over agents when the path is known. Determinism is cheaper, faster, debuggable."

Cross-cutting principles

  • 1. Start simple. A single well-prompted LLM call beats a misconfigured agent.
  • 2. Workflows over agents when the path is known. Determinism is cheaper.
  • 3. Tool design is most of the work. Names, descriptions, and schemas drive correctness.
  • 4. Cap your loops. Always have a maxSteps. Unbounded loops + flaky tools = unbounded cost.
  • 5. Make traces visible. You should be able to read the terminal and follow the agent's reasoning.
