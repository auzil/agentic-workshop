The Agent Loop

Workshop 01 of 5

Pattern: Augmented LLM + autonomous agent loop

Node.js 22  ·  TypeScript strict  ·  Azure OpenAI  ·  ~60 min

What is an agent?

An agent is an LLM in a loop.
On each turn, the model does exactly one of two things:

✓ Emits text

We're done. Return it to the caller.

⚙ Emits tool calls

Execute them, feed results back, loop.

That's the whole pattern. No framework needed.

Under the hood: function calling

The model doesn't run code. It emits structured JSON describing what to call. The API returns that as tool_calls instead of plain text.

You send

tools: [{
  type: 'function',
  function: {
    name: 'calculator',
    description: '...',
    parameters: { ... }
  }
}]

Model responds with

{
  "role": "assistant",
  "content": null,
  "tool_calls": [{
    "id": "call_abc123",
    "type": "function",
    "function": {
      "name": "calculator",
      "arguments": "{\"expression\":\"47*12\"}"
    }
  }]
}

arguments is a JSON string — parse with JSON.parse().

The loop

The model decides when it's done — loop exits on text, or when maxSteps is hit.

The conversation is a list

Everything the agent "knows" lives in ChatCompletionMessageParam[]. The loop is mostly bookkeeping over this array. 

// Four roles — the full vocabulary of a conversation
{ role: 'system',    content: '...' }
// ↑ model's persona — prepended once, present on every LLM call

{ role: 'user',      content: '...' }
// ↑ the human's input

{ role: 'assistant', content: null, tool_calls: [...] }
// ↑ model's turn when it wants to call tools — content is null here

{ role: 'tool',      tool_call_id: 'call_abc123', content: '{"result":564}' }
// ↑ one message per tool result, linked back by tool_call_id

Two shapes of response

response.choices[0].message takes one of exactly two forms.

Text answer — loop exits

{
  "role": "assistant",
  "content": "The answer is 564.",
  "tool_calls": undefined
}

tool_calls ?? [] is empty → return content.

Tool call — keep looping

{
  "role": "assistant",
  "content": null,
  "tool_calls": [{
    "id": "call_abc123",
    "function": {
      "name": "calculator",
      "arguments": "{\"expression\":\"47*12\"}"
    }
  }]
}

Execute, append results, call the LLM again.

The loop, step by step

  1. Init history: system + first user message.
  2. Call chat.completions.create with history + tool declarations.
  3. Read response.choices[0].message.
  4. tool_calls empty → log the text, return. Done.
  5. Append the assistant's tool-call turn to history.
  6. Execute each tool (Promise.all), append one role:'tool' message per result.
  7. Loop. Hit maxSteps → throw.

Why order matters

The API enforces a strict message sequence. Get it wrong → HTTP 400.

Turn 1 — you send

system "You are a math tutor…"
user "What is 47 * 12?"

↓ model replies with tool_calls

→

Turn 2 — you send

system "You are a math tutor…"
user "What is 47 * 12?"
assistant tool_calls: […] ← append FIRST
tool tool_call_id:"…" content:"564" ← THEN result

↓ model replies with final text

Tools: what the model sees

src/core/tool.ts — the Tool interface maps directly to the OpenAI function-calling spec. 

export interface Tool<TResult = unknown> {
  readonly name: string;         // function name the model calls
  readonly description: string;  // how the model decides WHEN to use it
  readonly parameters: ToolParameters; // JSON Schema — shapes the args
  readonly execute: (args: Record<string, unknown>) => Promise<TResult>;
}

Most agent failures are tool-design failures.
name, description, and parameter schema are the model's only interface to the outside world.

The calculator tool

src/tools/calculator.ts 

export const calculator: Tool<{ result: number }> = {
  name: 'calculator',
  description: 'Evaluate a mathematical expression and return the result.',
  parameters: {
    type: Type.OBJECT,
    properties: {
      expression: {
        type: Type.STRING,
        description: 'A valid JavaScript math expression, e.g. "47 * 12"',
      },
    },
    required: ['expression'],
  },
  execute({ expression }) {
    const result = Function(`'use strict'; return (${expression})`)();
    return { result: Number(result) };
  },
};

One door to the LLM

src/core/llm.ts — single point of Azure OpenAI access. Model name comes from .env — never hardcoded elsewhere. 

export const DEFAULT_MODEL = process.env['AZURE_OPENAI_MODEL'] ?? 'gpt-4o';

export function getLlm(): AzureOpenAI {
  // Lazily creates the client — importing this module at type-check time
  // does not require credentials to be set.
  const apiKey     = process.env['AZURE_OPENAI_API_KEY'];
  const endpoint   = process.env['AZURE_OPENAI_ENDPOINT'];
  const apiVersion = process.env['AZURE_OPENAI_API_VERSION'];
  // Throws with a clear message if any credential is missing
  instance = new AzureOpenAI({ apiKey, endpoint, apiVersion });
  return instance;
}

Azure OpenAI uses deployment names (e.g. gpt-4o) rather than model IDs. Set AZURE_OPENAI_MODEL in .env to match your deployment.

AgentConfig — what you pass in

src/core/agent.ts

export interface AgentConfig {
  readonly name: string;         // appears in every log line
  readonly instructions: string; // system prompt — the model's persona
  readonly tools?: readonly Tool[];
  readonly model?: string;       // defaults to DEFAULT_MODEL from .env
  readonly maxSteps?: number;    // hard cap — defaults to 10
}

// Typical instantiation:
const agent = new Agent({
  name: 'math-tutor',
  instructions: 'You are a careful math tutor. Use the calculator tool.',
  tools: [calculator],
});

Constructor is already implemented. Your job is run().

The exercise — 4 tasks

  1. Add the system message
    Prepend { role: 'system', content: this.instructions } to the history array.
  2. Write the loop
    Wrap the LLM call in for (let step = 0; step < this.maxSteps; step++). Throw after if no answer was produced.
  3. Handle tool calls
    Append the assistant turn first, then run each tool with Promise.all and return one role:'tool' message per result.
  4. Return the text answer
    When tool_calls is empty, log with this.logger.llmText and return.

Agent loop — when to use it

✓ Good fit

  • Open-ended problems where the number of steps is unknown upfront
  • Tasks that require the model to decide which tools to call and in what order
  • Research or exploration that may require backtracking

✗ Poor fit

  • Latency-sensitive tasks — each loop adds a full LLM round-trip
  • Fixed, known paths — use a workflow (W2–W4) instead
  • Untrusted environments where unbounded tool use is dangerous

"Workflows over agents when the path is known. Determinism is cheaper, faster, debuggable." — Anthropic

Cross-cutting principles

  • 1. Start simple. A single well-prompted LLM call beats a misconfigured agent.
  • 2. Workflows over agents when the path is known. Determinism is cheaper.
  • 3. Tool design is most of the work. Names, descriptions, and schemas decide correctness.
  • 4. Cap your loops. Unbounded loops + flaky tools = unbounded cost.
  • 5. Make traces visible. Read the terminal and follow the agent's reasoning.
